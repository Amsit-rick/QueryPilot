# DataFoundry 风格企业数据工作台改造计划

## 目标

将当前 Query Pilot 从“自然语言查询工具”升级为面向企业的数据任务工作台。目标是借鉴 DataFoundry 的产品形态和工程思路，而不是复制其代码或简单替换页面颜色。最终上线标准不以“功能能跑”为准，而以安全、可靠性、治理、可观测性和企业验收证据为准。

最终用户可以围绕一个数据任务完成语义理解、受控查询、多步分析、结果验证、图表或报告生成，并且能够保存、回放、审计和复用整个任务过程。

## 当前基线

当前项目已经具备以下基础能力：

- FastAPI 查询 API 和 Vue 工作台
- MySQL、SQLite 等数据源接入基础
- 登录、会话、租户和 RBAC
- 只读 SQL 校验、行级权限和字段脱敏
- 审批流程、审计日志和 CSV 导出
- Redis 检查点和导出任务
- LangGraph 运行时适配
- LangChain 模型适配和结构化 `SqlPlan`

当前主要限制是：查询仍以单次请求为中心，语义层较弱，前端仍以单个 `App.vue` 和视图状态切换为主，任务步骤、证据、结果资产和多步验证尚未形成统一模型。

## 分阶段实施计划

### 阶段一 工作台信息架构和前端拆分

优先级：P0

当前状态（2026-09-10）：**实现完成，真实后端全量验收待启动环境。** `/workspace`、`/tasks`、`/tasks/:id`、`/datasources`、`/approvals`、`/admin/users`、`/profile`、`/sessions` 均由真实路由页面组件和 `RouterView` 渲染，空壳路由已移除；页面展示、认证、查询、任务、数据源、审批、用户授权和账号会话均按组件/composable 分层。`App.vue` 已从页面堆叠收敛到 49 行的跨域装配层，路由刷新恢复、任务页、审批和权限管理独立 E2E 已通过。

目标：让页面从“查询页”变成真正的工作台，并消除所有功能堆叠在一个页面的问题。

任务：

- 引入 Vue Router，建立 `/workspace`、`/tasks`、`/tasks/:id`、`/datasources`、`/approvals`、`/admin/users`、`/profile` 页面。
- 抽离 `App.vue` 中的认证、查询、历史、用户管理、数据源和审批逻辑。
- 保留三栏工作台：左侧任务导航，中间任务画布，右侧任务检查器。
- 将“最近查询”改名为“最近任务”，显示任务标题、状态、时间和数据源。
- 增加空状态、加载状态、失败状态和长列表滚动策略。
- 确保用户管理、数据源管理和审批中心是独立页面，不再与查询画布混排。

验收标准：

- 初始页面无浏览器整体滚动条，任务画布位于中央。
- 点击侧边导航是真正的页面路由变化，而不是同页内容闪换。
- 刷新具体页面后仍能恢复当前路由和登录状态。
- 现有登录、查询、导出、审批和用户管理 E2E 不回归。

### 阶段二 DataTask 任务模型和持久化

优先级：P0

当前状态（2026-09-08）：后端闭环已完成。DataTask、TaskStep、TaskEvent、TaskArtifact 已具备内存与 MySQL 持久化实现，查询接口已接入任务生命周期并支持失败任务复用同一 `task_id` 重试。前端任务详情和步骤时间线待阶段一真实路由拆分后接入。

目标：把一次查询升级为可恢复、可回放、可审计的数据任务。

建议模型：

- `data_tasks`：任务标题、问题、创建者、租户、数据源、状态、时间。
- `task_steps`：步骤类型、输入、输出摘要、状态、耗时、重试次数。
- `task_artifacts`：表格、CSV、图表、报告、SQL 文件等结果资产。
- `task_events`：状态变化、工具调用、审批、错误和审计事件。

任务状态：

```text
draft → planning → running → verifying → completed
                         └→ approval_required
                         └→ failed / cancelled
```

验收标准：

- 一个任务可以在页面刷新或服务重启后继续查看。
- 历史记录按账号和租户隔离。
- 每个任务能查看完整 SQL、步骤、结果摘要和追踪 ID。
- 同一任务重复执行不会生成无法解释的重复历史记录。

### 阶段三 LangGraph 多步任务编排

优先级：P0

当前状态（2026-09-10）：受控实现完成，真实模型与外部数据库验收待补。自研 bounded Graph 与 LangGraph 均已具备独立语义解析、分析计划、结构化 `SqlPlan` 解析、SQL 校验、只读执行、结果验证、派生分析、结果解释、结果资产描述和有上限的自动修复循环；后处理仅接收已脱敏结果，失败不会回到 SQL 修复循环。`AnalysisPlan` 使用白名单分析模式和固定执行路径校验，API 可显式选择 `none` 或 `descriptive_statistics`，未知模式在执行前拒绝；关键词触发只作为兼容降级。`DerivedAnalysis`、`VerificationResult`、`ResultExplanation`、`ResultArtifact` 和语义上下文均进入 Graph 状态、checkpoint 与 DataTask 步骤。SQLite 受控验收已覆盖 `sales JOIN customers` 以及查询后描述统计的真实第二阶段执行。当前解释为明确标识的确定性摘要，表格资产持久化采用任务级幂等键。模型自主生成复杂联查、MySQL/PostgreSQL 两步执行和业务口径正确性仍不能据此宣称通过。

最新验证（2026-09-12）：真实模型已生成复杂 JOIN，并通过护栏及 SQLite 执行；MySQL 8.4 与 PostgreSQL 16 已完成 JOIN、Decimal 二阶段统计及专用只读账号写入拒绝。上述证据不证明业务口径正确或 Oracle 已适配。

目标：让 LangGraph 负责完整任务生命周期，而不是只包裹一次 SQL 生成。

节点建议：

```text
understand_question
    ↓
resolve_semantics
    ↓
plan_analysis
    ↓
generate_sql
    ↓
validate_sql
    ↓
execute_query
    ↓
verify_result
    ├── 需要修复 → generate_sql
    ├── 需要审批 → approval_required
    └── 通过 → explain_result
                    ↓
              materialize_artifacts
```

约束：

- 所有 SQL 仍必须经过现有校验、权限策略、行级过滤、字段脱敏和只读执行边界。
- 循环必须有最大步数、最大修复次数、超时和取消机制。
- 模型不能直接访问数据库连接或凭据。
- 每个节点输入输出都写入任务事件或检查点。

验收标准：

- 支持至少一个多表联查和一个两步分析案例。
- SQL 错误能够在限定次数内自动修复。
- 超时、服务重启、模型失败时任务状态可解释。
- 失败任务可以查看失败节点和错误原因。

### 阶段三补充 LangChain 深度化但保持轻量

优先级：P0

目标：让 LangChain 不止负责调用模型，同时避免引入难以调整的重型 Agent 框架。

LangChain 只承担可替换的认知和工具链：

- `ChatPromptTemplate` 和版本化 Prompt。
- `with_structured_output` 和 `SqlPlan`、`VerificationResult` 等契约。
- Schema Retriever 和企业语义 Retriever。
- 受控工具封装：`inspect_schema`、`resolve_metric`、`preview_table`、`execute_readonly_sql`、`verify_result`。
- SQL 生成链、结果验证链、结果解释链。
- Runnable 组合、模型路由、回调、Token 和成本统计。

LangChain 明确不承担以下职责：

- 不直接管理用户、租户、角色和审批权限。
- 不直接持有数据库连接、数据库密码或 Redis 密钥。
- 不绕过 FastAPI 的 SQL 校验、行级过滤、字段脱敏和只读边界。
- 不替代 LangGraph 的任务状态、循环、暂停、恢复和回放能力。

轻量化约束：

- 优先使用 LangChain Core、LangChain OpenAI 适配器和少量自定义 Runnable，不引入不必要的全家桶。
- 数据库工具使用项目自己的安全封装，不直接采用无法满足企业策略的通用 SQL Agent。
- 每条 LangChain 链都必须有清晰输入输出类型和单元测试。
- 所有链均可关闭或替换，模型不可用时有确定性降级路径。
- 业务规则保持在普通 Python 服务中，避免被框架隐式接管。

验收标准：

- Schema 和语义上下文通过检索注入，而不是无限扩大 Prompt。
- 查询、验证、解释分别是可独立测试和替换的链。
- LangGraph 能编排这些链，但链本身不依赖具体页面或数据库实现。
- 移除 LangChain 后，安全校验和数据库执行仍然可以独立运行。

### 阶段四 企业语义层

优先级：P1

目标：减少模型猜表、猜字段和指标口径漂移。

功能：

- 指标定义：名称、公式、粒度、时间口径、负责人、版本。
- 字段别名和业务术语映射。
- 表与表之间的关联路径和连接置信度。
- 默认过滤条件和敏感字段标记。
- 语义目录搜索和管理员维护页面。
- 查询时只向模型提供当前数据源允许的语义上下文。

验收标准：

- “销售额”“GMV”“活跃用户”等术语能映射到明确口径。
- 语义版本变化可以追踪。
- 未授权表和字段不会进入模型上下文。

### 阶段五 多数据源统一接入

优先级：P1

目标：将数据源从配置项升级为统一的 Data Gateway 抽象。

任务：

- 定义统一的数据源接口：连接测试、Schema、预览、查询、取消、健康检查。
- 完善 MySQL、PostgreSQL、SQLite、CSV 和 DuckDB 适配。
- 数据源凭据使用环境变量或密钥管理，不进入模型消息和普通日志。
- 数据源级权限、租户隔离和只读能力显式化。
- 为每种适配器增加契约测试。

验收标准：

- Agent 不需要知道具体驱动，只调用统一工具。
- 同一任务可以明确记录实际使用的数据源和方言。
- 连接失败时返回可操作的诊断信息。

### 阶段六 结果资产和可视化

优先级：P1

目标：让结果从页面临时表格升级为可复用资产。

功能：

- 表格、图表、CSV、SQL 和 Markdown 报告统一归档。
- 根据结果列类型推荐基础图表。
- 支持结果资产预览、下载、复制和再次引用。
- 后续问题可以引用之前任务中的表格或文本区域。
- 大结果集采用分页、异步导出和过期策略。

验收标准：

- 导出的文件与任务、用户和租户绑定。
- 下载权限经过再次校验。
- 结果资产有创建时间、来源步骤和数据版本信息。

### 阶段七 企业可靠性、评测和运营

优先级：P1

目标：让系统具备生产环境可观测、可限流、可回归验证的能力。

任务：

- 模型调用超时、重试、熔断和降级。
- 数据库和 Redis 健康检查、连接池和故障恢复。
- 查询、模型、导出和任务级指标。
- NL2SQL、权限、审批、历史隔离和导出回归测试集。
- 成本、Token、延迟和失败率统计。
- 结构化日志、trace_id、task_id 和审计导出。
- 生产部署、备份、恢复和迁移演练文档。

验收标准：

- 外部模型不可用时不会导致请求无限等待或无限重试。
- 服务重启后已持久化任务和审计记录不丢失。
- 关键安全回归测试在 CI 中执行。
- 可通过指标定位慢查询、模型失败和导出失败。

## 暂不纳入第一轮的内容

以下能力可以保留在后续版本，不作为首轮改造阻塞项：

- 28 种以上数据源的完整覆盖
- 自动化复杂图表设计
- 完全自主的长周期分析 Agent
- 外部 DataLink 或 MCP 生态集成
- 多区域高可用和 Kubernetes 部署

## 企业生产基线

以下项目不是可选优化，而是接入真实生产数据前的上线门禁。若目标企业已有统一平台，应优先接入企业标准，不重复建设同类能力。

### 身份和访问控制

- 接入企业 SSO（OIDC、SAML 或 LDAP），本地账号仅用于初始化和应急恢复。
- 支持组织、租户、用户、角色、数据源、表、字段和行级授权。
- 管理员、数据负责人、审批人和普通分析用户职责分离。
- 高风险查询支持二次确认、审批和强制审计。
- 会话支持过期、撤销、设备管理和异常登录告警。

### 密钥和数据安全

- 数据库密码、模型 API Key、Redis 密钥和 SMTP 凭据不得提交代码或写入前端。
- 生产环境使用企业密钥管理系统或 Vault，应用只获得短期凭据。
- 凭据不得进入 Prompt、LangGraph 状态、普通日志、导出文件或错误消息。
- 数据源使用最小权限账号，默认只读，并限制网络可达范围。
- 敏感字段采用分类分级、脱敏和按角色授权；导出同样执行权限检查。
- 对提示词注入、SQL 注入、越权查询和敏感数据外泄建立安全测试用例。

### 可靠性和容灾

- 为 API、数据库、Redis、模型服务和导出队列定义超时、重试、熔断、降级和取消策略。
- 查询和导出任务必须幂等，服务重启后可以恢复或明确失败，不能静默丢失。
- 明确 RPO、RTO、可用性目标、最大并发、最大查询时长和最大结果集。
- 执行数据库备份、恢复、故障切换和数据损坏演练，并保存演练记录。
- 核心组件至少有健康检查、依赖检查和启动前配置校验。

### 可观测性和运营

- 日志、指标和链路追踪统一接入企业平台。
- 每次任务关联 `tenant_id`、`user_id`、`task_id`、`trace_id`、模型版本和数据版本。
- 监控查询延迟、模型延迟、Token、成本、失败率、重试次数、队列积压和导出失败率。
- 配置告警阈值、值班责任人、事故分级和回滚操作手册。
- 审计记录保留周期、访问权限和导出机制符合企业要求。

### AI 质量和治理

- 固化模型、Prompt、工具 schema、语义目录和策略版本。
- 建立 NL2SQL、复杂联查、权限、脱敏、审批、错误修复和结果解释评测集。
- 每次模型或 Prompt 变更必须通过离线评测和关键回归测试。
- 记录模型输出、校验结果、人工修改、最终 SQL 和证据链。
- 对低置信度、高风险或结果异常任务自动转人工确认。
- 明确允许使用的数据范围、禁止回答的内容和人工复核责任。

## 企业验收门禁

每个门禁都必须有可保存的测试报告或配置证据，不能只凭页面演示通过。

| 门禁 | 必须证明的内容 | 通过条件 |
|---|---|---|
| 安全 | 身份、权限、密钥、注入、越权、脱敏 | 高风险用例无越权和敏感信息泄露 |
| 数据治理 | 指标口径、数据源责任、版本和血缘 | 关键指标可解释、可追溯 |
| 可靠性 | 超时、重试、熔断、恢复、幂等 | 故障可控，任务不静默丢失 |
| 性能 | 并发、延迟、结果集和队列容量 | 达到目标 SLO 并留有容量余量 |
| AI 质量 | NL2SQL、联查、修复和解释回归 | 关键评测集达到约定通过率 |
| 审计 | SQL、工具调用、审批、导出和管理员操作 | 事件完整、不可随意修改、可检索 |
| 运维 | 监控、告警、备份、恢复、回滚 | 值班人员可按手册处理故障 |
| 合规 | 数据分类、保留、访问和供应商要求 | 通过企业安全与合规评审 |

## 上线分级

### L0 开发环境

使用脱敏或合成数据，可使用本地账号和本地模型配置。禁止连接核心生产库。

### L1 部门试点

接入企业身份系统和一套只读数据源，完成权限、审计、恢复、评测和人工审批验证。结果仅供试点用户使用。

### L2 受控生产

完成生产密钥管理、监控告警、备份恢复、容量测试、事故手册和安全评审。只允许已批准的数据源和业务范围。

### L3 企业级平台

支持多租户治理、统一语义目录、多数据源、标准化 SLO、跨区域容灾、集中审计和持续评测。达到此级别前不能宣称为集团级通用平台。

## 技术决策

## 专业企业代码分层

目标是形成清晰的模块边界和单向依赖。拆分过程采用“先抽服务、再拆路由、最后移动文件”的方式，避免一次性重写导致功能回归。

### 目标目录结构

```text
app/
├── main.py                         # 应用装配、中间件和启动入口
├── config/                          # 配置读取、环境校验和密钥引用
│   ├── settings.py
│   └── logging.py
├── api/                             # HTTP 路由和请求响应模型
│   ├── dependencies.py
│   ├── auth_routes.py
│   ├── task_routes.py
│   ├── query_routes.py
│   ├── datasource_routes.py
│   ├── approval_routes.py
│   ├── admin_routes.py
│   └── export_routes.py
```

### 依赖方向

```text
api → services → domain
                 ↑
repositories ← infrastructure

api → schemas
services → repositories / agent / security
agent → domain contracts + 安全工具接口
infrastructure → 第三方 SDK 和数据库驱动
main → 所有模块的依赖注入和装配
```

必须遵守以下规则：

- `api` 不直接访问数据库、Redis 或模型 SDK。
- `domain` 不依赖 FastAPI、LangChain、LangGraph 或具体数据库驱动。
- `services` 负责用例编排，不把 HTTP 请求对象传入领域逻辑。
- `agent` 只能通过受控工具接口访问数据，不持有数据库凭据。
- `repositories` 定义持久化接口，具体数据库实现放在 `infrastructure`。
- `security` 是横向能力，所有查询、导出、审批和管理操作都必须经过它。
- `main.py` 不承载业务逻辑，只做应用装配。

### 迁移原则

- 保留现有 API 路径和响应字段，先保证兼容，再逐步引入 `DataTask` API。
- 每次只迁移一个垂直能力，例如“用户管理”或“查询任务”，迁移后立即运行对应测试。
- 旧模块在迁移期间通过兼容导出保留，确认无调用方后再删除。
- 数据库迁移必须可前进、可回滚，并提供旧数据转换脚本。
- 前端先抽取 API 客户端和组件，再引入路由，最后拆分页面和状态。
- LangChain 链、LangGraph 节点和安全工具都必须有独立单元测试。

### 分层验收

- 新增路由只能调用 Service，不得出现 SQL、模型调用或 Redis 操作。
- Service 可以在不启动 HTTP 服务的情况下通过单元测试。
- Agent 可以使用 Fake Tool 运行测试，不依赖真实数据库。
- Repository 可以替换 SQLite、MySQL 或 PostgreSQL 实现而不修改领域规则。
- 前端页面可以在 Mock API 下独立构建和测试。

### LangChain 和 LangGraph 的职责

- LangChain：模型适配、提示模板、结构化输出、工具封装、结果解释。
- LangGraph：任务状态、节点编排、循环、审批暂停、检查点、恢复和回放。
- FastAPI：认证、权限、数据源、任务 API、审计和文件下载。
- Vue：工作台、任务详情、管理控制台和结果展示。

不建议让 LangChain 或 LangGraph 绕过现有安全层直接执行 SQL。数据库访问必须集中经过受控工具和策略边界。

### 轻量架构原则

整体框架以“可替换、可测试、可降级”为约束：

```text
Vue 工作台
    ↓
FastAPI 控制面和安全边界
    ↓
LangGraph 任务状态机
    ↓
LangChain 认知链与受控工具
    ↓
FastAPI 数据访问服务
    ↓
MySQL / PostgreSQL / SQLite / 其他数据源
```

LangChain 和 LangGraph 是 Agent 能力层，不成为系统所有模块的基础依赖。认证、权限、审计、迁移、数据源连接和文件服务仍使用稳定、直接、易运维的普通服务代码。

### 提交策略

本计划不要求每个小步骤提交 Gitee。采用里程碑提交：

- 每完成一个 P0 阶段并通过对应测试，提交一次。
- 多个紧密相关的小改动合并为一个可回滚提交。
- 涉及数据库迁移、前端路由、Agent Runtime 或部署配置等较大变化时单独提交。
- 每次里程碑提交必须包含测试结果、影响范围和回滚说明。
- 未完成或未验证的半成品不单独推送到主分支。

## 首轮执行顺序

当前建议按以下顺序实施：

1. 抽取 API 客户端、Service 和 Repository 接口，先建立分层骨架。
2. 完成前端路由拆分和工作台页面组件化。
3. 设计并实现 `DataTask`、步骤和事件模型。
4. 将 LangGraph 扩展为多步任务状态机。
5. 增加 LangChain Schema/语义检索、受控 Tools 和结果验证链。
6. 增加任务详情、步骤时间线和任务恢复。
7. 建立最小企业语义层。
8. 再扩展多数据源、结果资产和运营能力。
9. 建立企业安全基线、可靠性演练和 AI 回归门禁。
10. 通过 L1 部门试点后，再评估 L2 受控生产，不直接跳到核心生产接入。
