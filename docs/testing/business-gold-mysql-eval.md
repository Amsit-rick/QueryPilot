# 真实业务评测：40 条问题跑真实 MySQL 与真实模型

本文记录 `data/business_gold_mysql.json` 的设计、执行方式和 2026-11-08 的结果。
它补充而不是替代合成评测：合成数据集验证分类与契约，这份数据集验证"真实数据库 + 真实模型"的端到端表现。

## 为什么单独做一套

此前的 Business Gold 只有 11 条，且执行在临时 SQLite fixture 上（6 张表、十几行数据）。这类评测适合固定
契约，但不能回答"模型在真实表结构和真实数据量上答对多少"。本套评测的目标是把这个问题变成一个可重复的数字。

它**不是**企业真实业务数据验收：数据库里是企业级合成演示数据（50 万级 order_items、25 万级订单），
问题由工程侧编写，没有业务负责人签字确认口径。因此结论只覆盖"这 40 条问题、这套合成数据、当前模型"。

## 数据集

- 版本：`business-gold-mysql-v1`，40 条中文业务问题，覆盖 9 个能力类别。
- 库表：`enterprise_orders`、`enterprise_customers`、`order_items`、`payments`、`inventory`、
  `products`、`suppliers`、`employees`（约 74 万行业务数据）。
- 形态：单表聚合、分组对比、比例计算、日期范围、Top N、多表 JOIN、LEFT JOIN 空值、CTE 预聚合。
- 每条用例包含 `id`、`category`、`question`、`gold_sql`，`ordered` 仅在题面明确要求排序时为 true。
- Gold SQL 必须先通过同一个 AST 护栏，再在真实库上执行成功且返回非空结果，才算用例有效。

## 执行方式

```cmd
:: 1) 只校验 Gold 自身：护栏 + 真实执行
.venv\Scripts\python.exe scripts\evaluate_business_gold_mysql.py --check-gold

:: 2) 完整评测：真实模型生成 -> 同一护栏 -> 真实只读执行 -> 结果比对
.venv\Scripts\python.exe scripts\evaluate_business_gold_mysql.py --output artifacts\business-gold-mysql.json

:: 3) 无模型密钥时应显式阻塞
.venv\Scripts\python.exe scripts\evaluate_business_gold_mysql.py --require-external
```

模型调用沿用生产链路 `AgentQueryService`（provider、prompt 版本、方言、参数绑定与线上一致），
生成结果仍必须通过 `validate_sql`；评测不绕过任何权限或只读边界。

## 比较规则（决定数字是否可信）

- 列别名忽略：`SUM(x) AS total` 与 `SUM(x) AS amount` 视为同一结果。
- 行顺序：只有 `ordered=true` 的 2 条用例（明确要求排序）才比较顺序，其余按行集合比较。
- 数值容差按量级分档：`|x| ≤ 1` 用 `1e-4`（比例/占比按 4 位小数），`|x| > 1` 用 `0.01`（金额/均值按 2 位小数）。
  这样可以接受 `ROUND(AVG(x),2)` 与全精度结果的差异，但不会把 `0.1988` 与 `0.2037` 判成相同。
- 口径：`result_exact_match_rate` 是**端到端**指标。生成失败、护栏拒绝、执行失败、结果不一致全部计为未命中，
  因此不会因为"拒绝了一条 SQL"而虚高。
- 报告不保存问题、SQL、参数值或结果行，只保存用例 ID、状态、稳定错误码、列数和耗时。

## 结果（2026-11-08，DeepSeek `deepseek-chat`，本机 MySQL 8.4）

| 指标 | 数值 |
|---|---|
| 用例数 | 40 |
| Gold 完整性 | 40/40 |
| 生成成功率 | 100% |
| 护栏通过率 | 97.5%（39/40） |
| 执行成功率 | 100%（护栏通过后） |
| **端到端结果一致率** | **72.5% / 72.5% / 75.0% / 77.5%（4 次重复运行，中位数 73.8%）** |
| 延迟 P50 / P95 | 2.60 s / 3.81 s（含模型生成与数据库执行） |

单次运行的明细报告见 `docs/evidence/business-gold-mysql.json`（它是一次抽样，不代表上界）。
同一数据集重复运行会上下浮动约 ±2.5 个百分点（±1 条用例），主要来自模型输出的列选择不稳定。

## 失败分布（9 条未命中，按原因归类）

| 类别 | 用例 | 说明 |
|---|---|---|
| 投影多余列 | BIZ-015、BIZ-037、BIZ-040 | 结果值正确，但多返回了 `customer_code`/`name`/`id` 等描述列；严格按列数比较记为未命中 |
| 参数值未接地 | BIZ-010、BIZ-036 | 把中文业务词直接当参数值（`'已支付'`、`payment_status='completed'`），库里是 `paid`，导致空结果 |
| 时间表示差异 | BIZ-002、BIZ-034 | 模型用 `DATE_FORMAT` 返回 `'2025-01'`，Gold 用 `MONTH()` 返回 `1`，分组与数值一致 |
| 不支持的 SQL 构造 | BIZ-032 | 模型用 `NOT EXISTS` 相关子查询，护栏不支持相关子查询，拒绝码为 `E_READONLY_VIOLATION` |
| 口径错误 | BIZ-012 | 退款占比的分母取成了"退款总额"而不是"全部支付总额" |

这张表本身比 73.8% 更有用：它把"模型不够好"拆成了四类可分别修的问题。

## 评测发现并修复的产品缺陷

1. **`MONTH(date_col)` / `DAY(date_col)` 被误拒**。SQLGlot 会把它们改写成 `CAST(col AS DATE)`
   （`TS_OR_DS_TO_DATE`），该节点不在函数白名单里，导致"每月趋势"这类最常见的问题直接
   `E_READONLY_VIOLATION`。已加入白名单并补 SQLite/MySQL 回归测试。
   修复前 Gold 完整性只有 38/40，等于这类问题在生产里也答不了。

2. **相关子查询不在支持范围**（未修复，已知限制）。`NOT EXISTS` 目前报"函数未在安全白名单中：EXISTS"，
   错误码与原因都不准确。支持相关子查询需要改写作用域解析，本轮不做；建议在文档和错误文案里
   明确"请改写为 LEFT JOIN 或 CTE"。

## 边界与不宣称

- 数据是企业级**合成**数据，不是真实业务数据，也没有业务负责人确认指标口径。
- 40 条问题由工程侧编写，不能代表全部问法；同义改写、模糊表述、多轮追问未覆盖。
- 只验证了 DeepSeek 一个模型和 MySQL 一种方言；没有跑 SQLite/PostgreSQL/Oracle 对照。
- 单机单实例，延迟数字不能作为生产容量结论。
- 端到端一致率低不代表系统不可用：护栏拒绝、参数未接地的 SQL 本来就不应该被执行。
  该指标衡量的是"能不能直接给出正确答案"，不是"安全不安全"。

## 2026-11-08 值接地实验（同一数据集，配对对比）

评测暴露的 `BIZ-008/010/036` 都是同一类问题：模型把中文业务词直接绑定成参数值（`已支付`），
库里存的是 `paid`，查询返回空。新增枚举值接地后（见 `docs/value-grounding.md`），配对运行结果：

| 配置 | 运行 1 | 运行 2 | 运行 3 | 中位数 |
|---|---|---|---|---|
| 关闭接地 | 72.5% | 75.0% | 72.5% | 72.5% |
| 开启接地（9 列） | **80.0%** | **80.0%** | **80.0%** | **80.0%** |

- 净增 **+7.5 个百分点**，三次运行一致；`E_EMPTY_RESULT` 从 1–2 降为 0。
- 同时验证了接地清单必须窄：第一版把 `region` 也纳入，导致 `BIZ-027` 稳定回退，去掉后恢复。
- 剩余 8 条失败与接地无关：多返回描述列 3 条、月份表示差异 2 条、口径偏差 2 条、
  不支持的相关子查询 1 条。
- 该数字仍只代表这 40 条合成业务问题与当前模型，不是企业真实业务准确率。


## 2026-11-08 留出集：30 条未参与调参的问题

前 40 条（`business_gold_mysql-v1`）是接地功能的开发集，用它衡量接地会高估收益。因此另建
`data/business_gold_mysql_holdout.json`：30 条题目在接地完成之后编写，未参与其设计，只用于检验泛化。
形态覆盖复合过滤、三表 JOIN、双维度分组、CASE 分桶、占比、LEFT JOIN 空值、交叉分组、字符串函数、
日期区间和 Top-N。

### 第一版题面有歧义（评测设计缺陷，已修正）

首轮运行发现 3 条分桶题、2 条比例题因"表示差异"失败，而不是模型答错：分桶标签没规定（low/high 还是中文？）、
比例单位没规定（0–1 还是百分比）、月份没规定（`1` 还是 `'2025-01'`）、Top-N 没规定并列规则。
这些是**出题不严谨**，已把单位、标签、月份表示和并列规则写死，Gold 仍 30/30 通过。

### 模型端点不稳定与有效性门禁

运行期间模型端点出现 `ConnectError`（约 15%–50%，直连与代理都一样）。评测加了有界重试（最多 7 次），
并在生成成功率低于 95% 时把报告标记为 `external_validation=inconclusive`
（原因码 `MODEL_CONNECTIVITY_UNSTABLE`），避免把网络问题写成模型准确率。下面只采用生成 100% 的运行。

### 结果（各 2 次，生成成功率 100%）

| 配置 | 运行 1 | 运行 2 |
|---|---|---|
| 关闭接地 | 86.7% | 86.7% |
| 开启接地 | **93.3%** | **93.3%** |

- 留出集上接地仍带来 **+6.7 个百分点**（26/30 → 28/30），说明收益不是开发集过拟合。
- 被修好的是 `H-001`（复合过滤，需要把"已完成"映射成 `completed`）等参数值接地问题。
- 剩余 2 条失败与接地无关：`H-009`（模型用 `NOT EXISTS` 相关子查询，护栏不支持）、
  `H-014`（评分分桶边界/标签表示差异）。

### 结论与边界

- 开发集 80.0%、留出集 93.3%，两者都只代表这 70 条合成业务问题与当前模型。
- 留出集更难的地方不在 SQL 复杂度，而在**题面表达**：单位、标签、口径不写死时，"正确"本身就没有定义。
- `NOT EXISTS` 与相关子查询仍是显式能力缺口，遇到会稳定计为失败。
